Diff between Tasks.Factory.StartNew and Task.Run(): From Gemini

While Task.Factory.StartNew() and Task.Run() both create and start a Task to execute work asynchronously, Task.Run() is generally the preferred and safer option in modern C# asynchronous programming, especially when using async and await.

Here's a detailed comparison:

Task.Run()
Simplicity and Convenience: Task.Run() is a simplified, static helper method introduced in .NET 4.5 specifically for the most common use case: offloading a CPU-bound operation to the ThreadPool. It handles the creation and immediate scheduling of the task.
Default Behavior: It uses sensible defaults:
Schedules the task to the TaskScheduler.Default (which typically targets the ThreadPool).
Uses TaskCreationOptions.DenyChildAttach, preventing child tasks from "attaching" to the parent, which helps avoid unexpected behavior and simplifies reasoning about task completion.
Automatically "unwraps" nested Task objects. If the delegate you pass to Task.Run returns a Task (e.g., you pass an async lambda), Task.Run will return a Task that represents the completion of the inner task, not a Task<Task>. This is crucial for correct async/await behavior.
Recommended for CPU-Bound Work: It's the go-to method for running synchronous, CPU-bound code on a background thread to keep the calling thread (e.g., a UI thread) responsive.
Works Well with async/await: Its default unwrapping behavior makes it seamless to use with async lambdas, where you might have an await inside the Task.Run delegate.

Task.Factory.StartNew()
Older, More Flexible, More Complex: Task.Factory.StartNew() existed before async/await and offers more flexibility, but with that flexibility comes increased complexity and potential pitfalls.
Customizable TaskCreationOptions: You can specify various TaskCreationOptions flags, such as:
TaskCreationOptions.LongRunning: Hints to the TaskScheduler that the task will be long-running and might benefit from a dedicated thread rather than a ThreadPool thread.
TaskCreationOptions.AttachedToParent: Allows a child task to be attached to its parent, meaning the parent won't complete until all its attached children complete. This can be useful for structured parallelism but is often misused.
TaskCreationOptions.PreferFairness, TaskCreationOptions.HideScheduler: More advanced options for controlling scheduling behavior.
Custom TaskScheduler: You can explicitly provide a TaskScheduler to control where the task is executed (e.g., a custom scheduler, a UI thread scheduler).
No Automatic Unwrapping for async Delegates (Crucial Difference): This is the most significant difference and the primary reason to prefer Task.Run(). If you pass an async delegate (a Func<Task> or Func<Task<TResult>>) to Task.Factory.StartNew(), it will not automatically unwrap the inner Task. This means Task.Factory.StartNew(() => SomeAsyncMethod()) will return a Task<Task> (or Task<Task<TResult>>), not a Task (or Task<TResult>). To get the desired behavior with await, you'd need to explicitly call .Unwrap(): await Task.Factory.StartNew(() => SomeAsyncMethod()).Unwrap(); Forgetting to Unwrap() is a common source of bugs and unexpected behavior.
Return Type: When the delegate doesn't return a Task (e.g., Action), Task.Factory.StartNew() returns a Task. If the delegate returns a value, it returns Task<TResult>. If the delegate returns a Task itself, it returns Task<Task> (as mentioned above).
